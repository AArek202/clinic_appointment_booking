# Shared Interface Contract

Binding names and signatures shared across the implementation plans. Plans are
executed in order but written independently, so this file is the single source of
truth for anything one plan produces and another consumes.

**If a plan disagrees with this file, this file wins.** Update it rather than
diverging.

---

# Conventions

- Database identifiers are `snake_case`; TypeScript is `camelCase`. Column names
  are declared explicitly (`@Column({ name: 'start_at' })`) rather than via a
  naming strategy, so the mapping is visible in the entity.
- Instants are `timestamptz` in PostgreSQL and `Date` in TypeScript.
- Wall-clock times are `time` in PostgreSQL and `string` in the form `'HH:mm:ss'`
  in TypeScript.
- Calendar dates crossing the API boundary are `string` in the form
  `'YYYY-MM-DD'`, interpreted in `CLINIC_TZ`.
- Primary keys are `uuid`, generated by PostgreSQL (`gen_random_uuid()`, built
  into PostgreSQL 13+; no `uuid-ossp` needed).
- Every entity file is `<name>.entity.ts` inside its feature folder.
- Every migration file is `src/database/migrations/<timestamp>-<Name>.ts` with a
  matching `name` property.

# Enums

All in `src/common/enums/`, one file each.

```ts
// role.enum.ts
export enum UserRole {
  Admin = 'ADMIN',
  Doctor = 'DOCTOR',
  Patient = 'PATIENT',
}

// appointment-status.enum.ts
export enum AppointmentStatus {
  Confirmed = 'CONFIRMED',
  Cancelled = 'CANCELLED',
}

// appointment-source.enum.ts
export enum AppointmentSource {
  Direct = 'DIRECT',
  WaitingList = 'WAITING_LIST',
}

// waiting-list-status.enum.ts
export enum WaitingListStatus {
  Waiting = 'WAITING',
  Assigned = 'ASSIGNED',
  Expired = 'EXPIRED',
  Cancelled = 'CANCELLED',
}

// notification-type.enum.ts
export enum NotificationType {
  Reminder = 'REMINDER',
  WaitlistAssigned = 'WAITLIST_ASSIGNED',
}

// notification-status.enum.ts
export enum NotificationStatus {
  Pending = 'PENDING',
  Sent = 'SENT',
}
```

Enums are stored as PostgreSQL `text` with a `CHECK` constraint rather than as
native `enum` types. Adding a value to a native PostgreSQL enum requires
`ALTER TYPE`, which cannot run inside a transaction in older versions and makes
migrations awkward; a `CHECK` constraint is trivially alterable and just as
strict.

# Database Error Helpers

Created in Plan 5, `src/common/errors/database-error.ts`:

```ts
/** PostgreSQL SQLSTATE codes we branch on. */
export const PG_UNIQUE_VIOLATION = '23505';
export const PG_EXCLUSION_VIOLATION = '23P01';

/** Extracts the SQLSTATE from a TypeORM QueryFailedError, or undefined. */
export function getSqlState(error: unknown): string | undefined;

/** Extracts the violated constraint name, or undefined. */
export function getConstraintName(error: unknown): string | undefined;

/** True when the error is a violation of the named constraint. */
export function isConstraintViolation(error: unknown, constraint: string): boolean;
```

All three exclusion constraints — both on `appointments` and `blocks_no_overlap`
— raise `23P01`, so callers must branch on `getConstraintName`, never on SQLSTATE
alone. See `docs/INFRASTRUCTURE/Concurrency.md`.

# Slot Logic (Plan 4)

Pure functions in `src/availability/slot-generator.ts`. No DI, no database
access — imported directly by both `AvailabilityService` and
`AppointmentsService`.

```ts
export interface Slot {
  startAt: Date;
  endAt: Date;
}

export interface TimeRange {
  startAt: Date;
  endAt: Date;
}

export interface ScheduleWindow {
  dayOfWeek: number;            // 0 = Sunday
  startTime: string;            // 'HH:mm:ss'
  endTime: string;              // 'HH:mm:ss'
  slotDurationMinutes: number;
}

export interface GenerateSlotsInput {
  fromDate: string;             // 'YYYY-MM-DD', clinic-local, inclusive
  toDate: string;               // 'YYYY-MM-DD', clinic-local, inclusive
  timeZone: string;             // CLINIC_TZ
  schedules: ScheduleWindow[];
  blocks: TimeRange[];
  booked: TimeRange[];
}

/**
 * Expands weekly schedules across the date range in clinic-local time,
 * converts each slot boundary to UTC, then removes slots overlapping a block
 * or an existing booking. Slots are half-open [startAt, endAt).
 * Returned in ascending startAt order.
 */
export function generateSlots(input: GenerateSlotsInput): Slot[];

/**
 * Resolves a requested instant to the slot it must occupy.
 *
 * Returns null when startAt falls outside every schedule window for that
 * weekday, or does not land exactly on a slot boundary generated by the
 * matching window's slotDurationMinutes.
 *
 * Used by booking to derive endAt and to reject off-grid requests. This is
 * layer 1 of the concurrency strategy (docs/INFRASTRUCTURE/Concurrency.md).
 */
export function resolveSlot(
  startAt: Date,
  schedules: ScheduleWindow[],
  timeZone: string,
): Slot | null;

/** True when the two half-open ranges overlap. */
export function overlaps(a: TimeRange, b: TimeRange): boolean;

export const MAX_AVAILABILITY_RANGE_DAYS = 62;
```

Consumed by Plans 4, 5, 7 and 8. Reproduced here because the exact names and

`Schedule` structurally satisfies `ScheduleWindow` below, so
`findByDoctorId` results can be passed straight to `generateSlots` and
`resolveSlot` with no mapping.

empty array is truthy, so `if (blocks)` would treat every slot as blocked.

```ts

  doctorId: string,
  year: number,
  month: number,
): Promise<DoctorMonthlyAnalytics>
```

Deliberately does no computation. It exists only to turn a missing doctor into a
404 and to keep the controller out of the repository. The response body is
`DoctorMonthlyAnalytics` serialised as-is.

Both rate fields are `COALESCE(ROUND(... / NULLIF(x, 0), 2), 0)` in SQL, so a
month with no appointments or no schedule returns `0`, never `null`.

# Queue Contract (Plan 6)

`src/jobs/queue.constants.ts`:

```ts
export const QUEUE_REMINDERS = 'reminders';
export const QUEUE_WAITING_LIST = 'waiting-list';
export const QUEUE_MAINTENANCE = 'maintenance';

export const JOB_SEND_REMINDER = 'send-reminder';
export const JOB_PROCESS_SLOT = 'process-slot';
export const JOB_RECONCILE = 'reconcile';

export interface SendReminderJobData {
  appointmentId: string;
}

export interface ProcessSlotJobData {
  doctorId: string;
  slotStartAtIso: string;
}

/** Deterministic id so duplicate enqueues for the same slot collapse into one. */
export function processSlotJobId(doctorId: string, slotStartAt: Date): string {
  return `waitlist:${doctorId}:${slotStartAt.toISOString()}`;
}

export function sendReminderJobId(appointmentId: string): string {
  return `reminder:${appointmentId}`;
}

export const RECONCILE_EVERY_MS = 60_000;
export const RECONCILE_SCHEDULER_ID = 'reconcile-sweeper';
export const RECONCILE_BATCH_LIMIT = 100;
export const WAITING_LIST_CANDIDATE_LIMIT = 10;

/**
 * Job id used when the sweeper re-enqueues a reminder.
 *
 * Deliberately not sendReminderJobId(): BullMQ ignores `add` for a job id that
 * already exists, and the original id may still be held by a job sitting in
 * the failed set. Bucketing by sweep interval keeps two replicas sweeping the
 * same minute from creating two jobs, while never being permanently blocked.
 * Duplicate delivery is prevented by markSentIfPending, not by this id.
 */
export function sweepReminderJobId(appointmentId: string, now: Date): string {
  const bucket = Math.floor(now.getTime() / RECONCILE_EVERY_MS);
  return `reminder-sweep:${appointmentId}:${bucket}`;
}
```

Job payloads carry identifiers only, never state. Workers re-derive every
decision from the database so a retry always acts on current data. See
`docs/INFRASTRUCTURE/BackgroundJobs.md`.

`JobsService` (`src/jobs/jobs.service.ts`) is the **only** enqueue surface:
`scheduleReminder`, `removeReminder`, `enqueueDueReminder`,
`enqueueSlotProcessing`. Feature services must not `@InjectQueue`.

# Foreign Key Delete Rules

Not uniform, and the difference is intentional:

- `ON DELETE RESTRICT` for `doctors.user_id`, `patients.user_id`,
  `appointments.doctor_id`, `appointments.patient_id`,
  `waiting_list.doctor_id`, `waiting_list.patient_id`. These rows carry history
  or identity, and losing them to a cascade would be data loss.
- `ON DELETE CASCADE` for `schedules.doctor_id` and `blocks.doctor_id`. These
  are owned configuration with no historical value; a doctor's working hours
  mean nothing without the doctor.

The rule: cascade configuration, restrict history.
