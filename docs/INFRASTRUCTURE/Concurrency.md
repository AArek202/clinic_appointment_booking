# Concurrency Strategy

## Problem

Multiple API instances may receive booking requests for the same slot simultaneously.

Example:

Patient A → API instance 1 → PostgreSQL
Patient B → API instance 2 → PostgreSQL

Both requests may see:

"slot is available"

If the application only checks availability before inserting, both may succeed.

---

# Required Invariant

For a given doctor:

No two CONFIRMED appointments may overlap in time.

Note that this is stated as *overlap*, not *equal start time*. That distinction is
the reason for the solution below.

---

# Decided Solution: Two Layers

## Layer 1 — Canonical slot identity (application)

Every booking request is snapped to the doctor's slot grid before it reaches the
database. A request is rejected with 400 unless its `start_at`:

1. falls inside a `schedules` row for that weekday, and
2. lands exactly on a slot boundary generated by that row's `slot_duration_minutes`.

`end_at` is always derived by the server from the schedule's slot duration. It is
never accepted from the client.

This keeps every row on a predictable grid, which is what makes availability
listing and analytics meaningful.

## Layer 2 — Exclusion constraint (database)

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments ADD CONSTRAINT appointments_no_overlap
  EXCLUDE USING gist (
    doctor_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  ) WHERE (status = 'CONFIRMED');
```

## Why not a partial unique index alone?

A partial `UNIQUE (doctor_id, start_at) WHERE status = 'CONFIRMED'` prevents two
appointments with the *identical* start time, which is enough for the simple
"two patients, same slot" race. It is not enough for this schema, for two
reasons documented in `docs/FEATURES/Schedules.md`:

- Slot duration lives on each schedule row, and different weekdays may use
  different durations.
- Changing a schedule's slot duration must not rewrite historical appointments.

So a doctor can legitimately hold a 30-minute appointment at 10:00 while the
schedule is later changed to 15-minute slots. A booking at 10:15 then has a
distinct `start_at` and passes a unique index cleanly, while overlapping a real
appointment. The exclusion constraint rejects it; a unique index does not.

The exclusion constraint is a strict superset of the unique index for this
invariant, so only the exclusion constraint is created.

---

# Why Database-Level Protection?

Application-level checks are vulnerable to race conditions.

Database constraints operate correctly even when:

- multiple NestJS instances exist
- multiple requests arrive simultaneously
- requests run on different processes
- requests run on different machines

---

# Application Behavior

Normal booking:

1. Validate request.
2. Validate schedule and slot-grid alignment.
3. Validate blocked periods.
4. Attempt INSERT.
5. PostgreSQL enforces non-overlap.
6. If the constraint rejects the insert, return 409 Conflict.

## Error mapping

The insert is attempted and the failure is handled. There is no
check-then-insert, because that is the race itself.

Map by SQLSTATE **and constraint name**, never by matching error message text:

- `23P01` on `appointments_no_overlap` -> 409, `SLOT_ALREADY_BOOKED`
- `23P01` on `appointments_patient_no_overlap` -> 409, `PATIENT_ALREADY_BOOKED`
- `23P01` on `blocks_no_overlap` -> 409, `BLOCK_OVERLAP`
- `23505` on `waiting_list_one_active` -> 409, `ALREADY_IN_WAITING_LIST`
- `23505` on `notifications_unique_per_type` -> not an error; the job treats it as "already done"

`blocks_no_overlap` is listed for completeness. Block creation has no concurrency
pressure — a doctor does not race themselves to record the same absence twice —
so in practice the service's own overlap lookup returns `BLOCK_OVERLAP` first,
and the constraint is what keeps the table correct no matter who writes to it.
See `docs/DECISIONS.md` #18.

The constraint name is required, not optional detail. Both appointment
constraints raise the same SQLSTATE while meaning different things: one says the
doctor's slot is gone, the other says this patient is busy elsewhere. Reporting
"slot already booked" for the second would be actively misleading, and the
waiting-list job needs the distinction to decide whether to stop or move on.

Any other constraint violation must propagate as a 500 rather than being
reported as a booking conflict. A broad `catch` that turns every database error
into "slot taken" hides real bugs.

# Alternatives Considered

## Application-level check

Rejected as the only protection.

Reason:

Race condition between SELECT and INSERT.

---

## Pessimistic locking

Possible, but requires choosing and consistently locking the correct rows.

There may not be an appointment row to lock when the slot is empty.

Therefore it is more complicated for this use case.

---

## Partial unique index on (doctor_id, start_at)

Rejected as insufficient. See "Why not a partial unique index alone?" above.

---

## PostgreSQL advisory locks

Considered. `pg_advisory_xact_lock(hashtext(doctor_id || start_at))` would
serialize bookings per slot inside a transaction and needs no extension.

Rejected because it protects only the code paths that remember to take the lock.
The exclusion constraint protects the table itself, including the waiting-list
assignment job, the seed script and manual `psql` access. Hash collisions would
also silently serialize unrelated slots.

---

## Redis distributed lock

Not preferred as the primary source of truth.

Redis can coordinate application instances, but PostgreSQL already owns appointment consistency.

A distributed lock also introduces another failure mode: if Redis is unavailable
the lock cannot be taken, and the system must then either stop accepting bookings
or fall back to the database guarantee — in which case the database guarantee was
the real protection all along.

---

# Conclusion

PostgreSQL should enforce the booking invariant.

The application can perform normal availability checks, but the database is the final authority.

---

# Proof

The repository must contain a concurrency test that sends multiple simultaneous
booking requests for the same slot.

Decided: the proof runs against **multiple API instances behind a load balancer**,
because that is the threat model the task describes. `docker-compose` starts two
or more replicas of the app behind nginx, and the script fires its concurrent
requests at nginx.

Expected assertions — all three, not just the first:

1. Exactly one request returns 201.
2. Every other request returns 409, not 500. A 500 means the constraint fired but
   the error mapping did not.
3. The database contains exactly one CONFIRMED appointment for that slot.

Example expectation:

```text
Successful bookings: 1
Conflicted bookings (409): 9
Unexpected errors (5xx): 0
Confirmed appointments in DB: 1
```
